ARPG 学习日志 Day 9：八天功能复盘 —— 演进、选型与优化清单

2026 年 10 月 20 日更新于 2026 年 10 月 20 日约 1964 字6 分钟阅读UnityARPG游戏开发复盘阶段总结

背景与目标

八天时间，ARPGbegin 从一个空 2D 模板长成一个能跑的原型：人物能走、地图能钻山洞、敌人会追会打、玩家能挥剑、数值集中管理、杀怪能升级、UI 有了统一父节点和一块技能面板骨架。

这一篇不复述每天做了什么（前八篇各自写过），而是回答三个问题：

  • 八个功能之间是怎么互相咬合的？哪些是必需的顺序，哪些只是当时的顺手？
  • 八天里技术选型变了几次？为什么变？
  • 当前代码里有哪些明确知道、但还没还的债？

实现要点

一、八天横向对比

各天用到的脚本与数值，在前八篇里各自列过。三个数字先摆在这：12 个脚本、567 行、8 天，平均每天 70 行——其中一天是 0 行。

二、功能的四条演进主线

八个功能看着是每天独立加一块，实际沿着四条线往前推，每条线都有明确的触发条件：

1. 移动 → 碰撞 → 空间

移动（Day 1）→ 七层瓦片（Day 2）。人物能走之后第一个问题是「走不过去」和「被挡住看不见」，于是才有了分层。

2. 相机 → 感知 → 攻击

相机与追击（Day 3）→ 主动感知（Day 4）。镜头能跟着人走之后，才看得清「敌人从哪来」；看清之后才要求敌人「该发现你的时候发现你」。

3. 战斗 → 数值 → 成长

挥剑受击（Day 5）→ 属性单例（Day 6）→ 经验升级（Day 7）。打起来之后，第一个冒出来的需求不是「更好玩」，而是「伤害值散在四处没法调」。

4. 表现 → 界面

暂停面板（Day 6）→ UI 收拢（Day 8）。UI 一旦出现第二块，层级和排序就必须显式管理。

这四条线里，只有第 3 条是严格的因果链（没战斗就不需要属性，没属性升级毫无意义）。第 1、2、4 条更多是「做到这一步自然会撞上」，换个顺序也成立。

三、技术选型的三次转向

1. 数据归属：每个脚本各存一份 → StatsManger 单例集中

触发点是调一次平衡要改四个 Inspector。转向之后，「数值在哪」这个问题只有一个答案。

2. 模块通信：A 直接调 B → static event 广播

触发点是结算伤害的 Player_Combat 不该知道谁在涨经验。转向之后，新增一个订阅者不用动敌人。

3. 感知方式：OnCollisionEnter2D → OverlapCircleAll

触发点是碰撞只能表达「贴上了」，表达不了「看见你了」。转向之后，检测半径和攻击半径可以分开配。

三次转向的共同点：都是被具体问题逼出来的，不是提前设计的。反过来看，凡是提前设计的地方（比如 Day 3 就把 Attacking / knockback 两个状态写进枚举占位），后面确实省了事。

还有一条隐性的选型贯穿始终：表现层交给动画。伤害结算挂在动画事件上（Day 5）、HP 数字跳动交给 Animator（Day 3）、技能面板放在布局系统里而不是手摆坐标（Day 8）。能用编辑器配的，就不写代码算。

四、可优化方向

按「会不会立刻影响可玩性」分三级。

P0 —— 现在就是错的，必须先修

  • Enemy_Combat.damage 在场景里被序列化成 0：敌人会攻击、动画会播、ChangeHealth(0) 会调，但血量永远不掉，PlayerHealth 的死亡分支从未执行。
  • StatsCanvas 的 CanvasGroup.alpha 在 Day 8 搬层级时回到 1：属性面板从第一帧就盖在屏幕上。

P1 —— 功能正确但撑不住扩展

  • OverlapCircleAll 每帧分配数组，改用 NonAlloc 版本 + 复用缓冲区。
  • enemies[0] / hits[0] 只结算第一个命中目标，多敌同屏立刻失真。
  • 朝向用 localScale 符号判断，父级一旦有缩放就失效；应改用 facingDirection 作为单一真相，localScale 只做表现。
  • Enemy_Knockback.Knockback() 无重入保护，连续受击会叠加协程。
  • LevelUp() 用 if 而非 while，一次性大额经验会被吞。
  • StatsUI 槽位用下标 0/1 硬编码，加属性要重排数组。

P2 —— 不紧急，但会让后来的人踩坑

  • 两棵树下各有一个 CombatPanel，SkillSTile 是复制时留下的拼写。
  • Enemy_Movement.Attack() 是 Debug.Log 空壳，和 Enemy_Combat.Attack() 同名并存。
  • ExpManager 里的 KeyCode.Return 调试入口没删。
  • 七个 Tilemap 只有三个带 TilemapCollider2D，且没有 CompositeCollider2D，沿砖缝走路会轻微绊。
  • 技能面板没有开关，也没有 CanvasGroup 控制器。
  • Elevation_Entry / Exit 的 sortingOrder 分别是 15 和 10，不对称且无统一约定。

五、下一阶段的三条路

按投入产出排：

  1. 修完 P0（半小时）：让「能打掉血」和「开局不糊屏」成立，原型才谈得上可玩。
  2. 把技能面板接上数据（1–2 天）：level 已经存在，缺的是「升级给点数 → 点数写入 StatsManger → 面板刷新」这条链。这条路能立刻让 Day 7 的等级从展示变功能。
  3. 加第二个敌人（半天）：单敌场景掩盖了 hits[0]、协程重入、每帧分配三个问题，第二只怪一出现它们全会暴露。这是性价比最高的一次压力测试。

小结

八天做完的事，用一句话概括：把一个「能动」的场景，做成了一个「有状态」的系统。

功能清单是表层，真正沉淀下来的是三件事的性质在这八天里被各踩了一遍——

  • 数据放在哪：从散落在各脚本，到单例集中（Day 6）
  • 消息怎么传：从直接调用，到事件广播（Day 7）
  • 状态谁说了算：从一堆 bool，到枚举 + ChangeState（Day 3）

这三件事在第一个功能里就要做选择，而当时往往只能凭直觉选。复盘的意义不是后悔当初，而是知道现在这套选择在哪会疼——P0 / P1 / P2 那份清单，就是疼点的位置。
